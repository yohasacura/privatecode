## Tier A — do now

### A1. Formatter shell injection + formatter dead in multi-folder workspaces
`core/src/format/runner.ts:59` and `:66` (merges findings 30 + 31 — one function, one edit)

**Injection.** `rule.command.split('$FILE').join(relativePath)` is plain substitution, and the result goes to `powershell.exe -Command` (`powershell.ts:20-25`). `relativePath` is the model's own `args.path` (`edit-file.ts:314`). `write_file({path:'src/a;calc.exe;b.ts'})` passes every jail check — `assertSegmentAllowed` rejects only `:` and the eight DENIED_SEGMENTS (`workspace.ts:47-56,99-118`) — then the next `edit_file` runs `npx prettier --write src/a;calc.exe;b.ts`, where `;` is a PowerShell statement separator. The formatter is deliberately **not** permission-gated (it runs inside `edit_file.execute`, after `loop.ts:1166` already decided), so in auto-edit this is ungated arbitrary execution with no card. `config.ts:12-16` argues safety from "the command comes from a file the MODEL cannot write" — true of the command, false of its argument. Benign variant is far more common: a space or `&` in a filename breaks the command, and three failures (`MAX_FAILURES = 3`, `runner.ts:24,47`) disable the formatter for the whole session.

**Multi-folder.** `cwd: workspace.root` is `mounts[0].root` (primary only, `workspace.ts:165-167`), while `relativePath` in a multi-folder workspace is mandatorily `<mountName>/rest` (`workspace.ts:236-266`). Mounts provably never overlap (`mounts.ts:303-309`), so the path never exists under the primary root. Every edit in an attached folder appends `the formatter (...) exited 2` to the model's result; three of them kill the formatter for the primary folder too. `formatter.test.ts` uses `new Workspace(root)` only (lines 62, 97, 116).

**Fix.** Split the rule's command into exe + argv at config load and spawn with execa's array form (no shell parses the path at all); if the shell string must stay, substitute `$FILE` as a PowerShell single-quoted literal (`'` + `path.replace(/'/g,"''")` + `'`). Same edit: `const mount = workspace.mountFor(abs)` (exists, `workspace.ts:204-210`, currently uncalled by runner.ts) → `cwd: mount?.root ?? workspace.root`, substituting the mount-relative path. Add a two-mount formatter test.

### A2. `.privatecode/` write deny never fires in a multi-folder workspace
`core/src/permissions/engine.ts:194` (finding 28)

`PRIVATE_DIR_PATH = /^\.privatecode([\\/]|$)/i` is start-anchored. In a multi-folder workspace the model *must* prefix the mount name, so the only spelling it can write is `proj/.privatecode/settings.json` — which canonicalizes fine and fails the anchored test; the unanchored `ANY_PRIVATE_DIR_SEGMENT` is consulted only when canonicalization *fails* (`engine.ts:194-195`). Verified by re-running the regex: `.privatecode/settings.json` → denied, `proj/.privatecode/settings.json` → allowed. The jail does not backstop it (`.privatecode`, `settings.json` are in no DENIED_SEGMENTS; workspace.ts contains no `.privatecode` reference at all). The write lands, and the next session loads those `permissions`, `hooks` and `format` rules — hooks and format commands run through `runPowershell` with **no permission gate** (`hooks.ts:126-130`, `runner.ts:65`). In auto-edit/autopilot no card is shown at all.

**Fix.** Test the canonicalized path with `ANY_PRIVATE_DIR_SEGMENT` too (a `.privatecode` segment anywhere in a workspace-relative path is never a legitimate model write). Add a multi-folder case to `plan-mode-desync.test.ts:56-68`, which currently uses single-folder spellings only.

### A3. `sql_deploy` matches no permission family → publishes to a live DB with no card
`core/src/permissions/engine.ts:412` (finding 29)

`decide()` skips HARD_DENY (no `key.command`), skips the private-dir deny (not in FILE_WRITE_TOOLS), finds no rule, and falls to `modeDefault`. The `normal` arm asks only for FILE_WRITE_TOOLS / EXEC_TOOLS / `isExternalTool` — `sql_deploy` is in none, so it returns `{verdict:'allow', reason:'normal mode'}`. `sqlDeployTool.permissionKey` returns `{tool, target: args.action}`, and `target` is consulted by no family and by no unspec'd rule (`acceptsSpec`, `engine.ts:85-90`, doesn't list it). `sql_deploy({action:'publish'})` alters a live schema with no approval, in normal **and** auto-edit. Its own doc comment claims it is "gated on every use in every other mode"; DESIGN.md §6 records this exact fall-through as the defect that motivated `isExternalTool` — the fix covered MCP, and `sql_deploy` landed after it.

**Fix.** Invert the default: `modeDefault` asks for any tool that does not declare `readOnly: true`, rather than allowing anything not on a hand-maintained list. Minimum viable: a fourth family for out-of-workspace mutations containing `sql_deploy`, `ask` in normal/auto-edit, `allow` in autopilot, `deny` in plan; add it to `acceptsSpec`. Add an ask-verdict test (`default-set.test.ts:38-46` only checks plan-mode absence).

### A4. The acceptance gate treats an *incomplete* audit as a full pass
`core/src/session/contract.ts:998`, `core/src/session/session.ts:960` (finding 1)

`parseAcceptance` derives `met`/`unmet` only from the items the model returned; its sole emptiness guard is `if (met === 0 && unmet.length === 0) return null`, so a report covering 3 of 5 criteria parses clean. `resolveReportedCriteria` (`contract.ts:775-786`) iterates only `report.unmet`, so a criterion no item mentions never enters `unmetByIndex`; `renderCheckedState` (`contract.ts:802-811`) then does `if (why === undefined) met.push(i+1)` — **absence of a report is literally indistinguishable from an affirmation**. `session.ts:960` is `if (report.unmet.length === 0) { clean = true; break }`; nothing anywhere compares coverage against `contract.criteria.length` (grep hits only `seedTodos` 2357-2358 and `foldAnswer` 1267). ACCEPTANCE_TOOL's `items` array carries no `minItems`, so the grammar cannot force one item per criterion. Terminal consequence: `checkedState = '1,2,3,4,5 met'` promoted into message 0 at every later compaction, all plan items ticked, `contract.satisfied = true`, plan store emptied, verify strip reads `3 met, 0 unmet — ok` over a 5-criterion contract. This is the failure the file's own header names.

**Fix.** In `acceptanceGate` before line 960, resolve *every* item (met ones included) to a criterion index with `matchCriterionIndex`; any criterion index no item resolved to is UNMET with reason "the audit did not report on this criterion". Only `report.unmet.length === 0 && everyCriterionCovered` may set `clean`. `renderCheckedState` should render three states, not two: met / unmet / not reported.

### A5. Plan card can never un-tick, so it contradicts the contract note
`core/src/session/session.ts:2399` (finding 4 — same data as A4, ship together)

`syncTodosWithAudit` is `if (t.status === 'completed' || !met.has(t.text)) return {...t}` — a completed item is never re-opened, and `grep "status:"` over session.ts yields only the seeder's `'pending'` (2370) and `'completed'` (2402). `contract.checkedState` *is* recomputed wholesale each round (`session.ts:954`), and `MAX_ACCEPTANCE_ROUNDS = 2` with a comment anticipating round 2 changing a verdict — so the note moves backwards while the card cannot. The user ends up looking at a 4/4 plan card beside a note saying criterion 2 is UNMET. Worse: `planFinished` (`session.ts:934`) then reads the plan as complete forever, so **every subsequent turn in the session opens the audit** whether or not the model claimed anything. The doc comment at 2381-2383 asserts the opposite invariant.

**Fix.** Make it set state, not accumulate: for each scaffolded item matching a criterion, `completed` when its index is absent from `unmetByIndex`, `pending` when present. Leave model-written items alone.

### A6. The fresh-context diff reviewer has no step result budget — a large review silently doesn't happen
`core/src/session/session.ts:1088` (finding 2)

`runReviewer`'s `agentOpts` sets client, registry, context, transcript, mode, allowedTools, maxSteps and events — and **no** `stepResultBudgetChars`. `loop.ts:733` reads the option and skips the guard entirely when undefined. `grep 'new Agent('` returns exactly two constructions; only the main one (`session.ts:3388`) gets `tailBudgetTokens(contextLength) * 4`, under a comment reading "the moment one may exceed it, a step can bury the whole window. Watched happen at 131,072: twelve batched reads, HTTP 400". ### A7. A verbatim code quote spanning a comment line is rejected and mislabelled
`core/src/session/premises.ts:250` (finding 7)

`premises.ts:235` builds `{ code: normaliseCode(stripComments(text)), full: normaliseCode(text) }` — `stripComments` is applied to the file, never to `premise.quote`. `quoteIsInFile`'s loose pass keeps every line ≥ 8 chars as *required* evidence (`premises.ts:178,185`), so a comment line inside a genuine multi-line quote must appear in the comment-stripped view and cannot. It then matches `content.full` and the model is told "those lines are only in a COMMENT there, not in the code". Reproduced by running the two exported pure functions on a 4-line quote spanning one comment: `quoteIsInFile(quote, code) === false`, `(quote, full) === true`. `session.ts:1163-1175` returns `premiseFailureMessage`, and `loop.ts:757-768` turns that into `halted` — the whole batched step dies, every queued edit discarded, and the model re-reads files it read correctly. In this repo (roughly half comment by line count) almost every multi-line quote hits it. `premises.test.ts:237` only asserts a single fragment.

**Fix.** Strip comments from both sides: `quoteIsInFile(stripComments(premise.quote), content.code)`; reach the comment-only branch only when the stripped quote has no non-comment evidence left. Equivalently, drop pure-comment lines from `evidence` in the loose pass.

### A8. The server-death retry never re-arms the step clock, so the relaunched server's cold prefill is killed as a timeout
`core/src/agent/loop.ts:1093` (finding 12)

The retry branch is a bare `continue`; the only two `clock.beforeRequest` calls are `loop.ts:853` and `:871` inside `runStep`, and `chat()`'s clock parameter is typed `{signal; touch()}` — `beforeRequest` is unreachable from the retry. After a mid-generation death, deltas already called `touch()`, which sets `awaitingFirstToken = false` and arms `steadyMs` (90 s). `waitHealthy` burns ~20-30 s of that on the model reload. The relaunched process has an empty KV cache, so the retried request must prefill the whole prompt at `PREFILL_MS_PER_TOKEN = 4` — only ~16-27k tokens fit in the ~60 s left. `fire()` (`loop.ts:946`) short-circuits to `quiet()` because `awaitingFirstToken` is false, so it never even probes `/slots`: the prefill extension written for exactly this silence is bypassed. Turn dies with "passed its 90 s time limit" against a perfectly healthy server. The app's own reducer re-arms for this wait (`state.ts:797-804`); the core does not. `loop.test.ts:213-231` uses an instant fake server.

**Fix.** Widen `chat()`'s clock parameter to include `beforeRequest`; in the retry branch set `this.charsAtLastRequest = 0` and call `clock.beforeRequest(this.firstTokenBudget(this.opts.stepTimeoutMs))`. That also restores `awaitingFirstToken = true`, putting the `/slots` extension back in play.

`core/src/agent/loop.ts:759` (finding 15)

`const instead = await this.opts.onBeforeTool?.(...)` sits between the assistant append (`loop.ts:687`) and `this.answer(call, ...)`, with no try/catch — while the permission gate twelve lines below wraps its host boundary at `loop.ts:1250-1256` for precisely this reason. `session.ts:3310` wires `onBeforeTool` to `understandingGate`; inside it only `statePremises`, `readThroughLenses` and `port.askUser` are guarded — the three `store.saveMeta(this.meta)` calls (1162, 1220, 1277) are not, and `SessionStore.saveMeta` (`store.ts:234-237`) is a bare `ensureDir()` + `writeFileSync`. ### B1. Make the prompt-visible tool block a session constant — the single biggest speed lever
`core/src/llama/client.ts:140` (merges findings 17 + 5 + 21) — **~5-7 min per task turn at 40k context**

Every harness sub-call ships a **one-tool** `tools` array over the **live, unclipped** transcript: `checkAcceptance` (`contract.ts:967`), `statePremises` (`premises.ts:301`), `readOnce` ×3 (`understanding.ts:178`). With `--jinja` the Qwen template renders tools into message 0, so the longest common prefix ends right after message 0's prose and everything after is re-read. The codebase asserts the mechanism itself at `session.ts:3113-3116` ("the rendered tool schemas are part of the prompt, so a prewarm without them warms a prompt no step will ever send"), and `session.ts:2822-2825` records the 2026-08-16 spike finding that a restored slot does not re-arm prefix matching.

Measured: `registry.schemas()` serialises to 17,776 chars (~4.4k tokens). On a 40k-token transcript with ~5k shared prose, each divergent call costs `35,000 × 1.83 ms = 64 s`. Divergent calls on the live transcript per completed task turn: premise, reading #1, resume-main, acceptance r1, fixer resume, acceptance r2, fixer resume ≈ **7 × 64 s ≈ 450 s**. Scales linearly with context: at 100k it is ~183 s each.

Two module comments are false by this repo's own measurement (`contract.ts:164-171`: "carrying it all paid a full re-prefill (minutes, on a fat session)") and should be corrected in the same change: `premises.ts:274-276` "this costs one generation and no new prefill worth counting", and `understanding.ts:145-149` / `:305-307`'s claim that the readings sit on the conversation's cached prefix. *(The "three readings, one prefill between them" half of that comment is correct — readings 2 and 3 do share the READING_TOOL prefix.)* The call sites are honest: `session.ts:941-944`, `1163-1164`, `1222-1225` all flag `promptCacheCold` — this is a known-cost design, not a hidden bug.

**Fix.** Register the nine harness schemas (CONTRACT, PLAN, ACCEPTANCE, PREMISE, READING, GROUP, REVIEW, IMPROVE, EXPAND — 8,341 chars ≈ 2.1k tokens) alongside the workspace tools and send that identical array on **every** request; select the required tool with a named `tool_choice` (`{type:'function',function:{name:'report_acceptance'}}`). `ChatRequest.toolChoice` (`llama/types.ts:33`) is typed `'auto'|'required'|'none'` and needs widening. **Verify with one curl that the server accepts a named choice before committing**; if not, fall back to `tool_choice:'required'` over the constant array plus the existing `call.function.name !== …` check. Cost: +2.1k tokens in the prefix, paid once per session (3.9 s).

**Interim, if B1 is deferred** (finding 5, small): give `statePremises` and `readOnce` the *same* list — `tools: [PREMISE_TOOL, READING_TOOL]` on both — so the premise call and the three readings ride one prefix instead of two. Removes one full cold prefill per task (~64 s at 40k, ~183 s at 100k) with a two-line diff, because the divergent final user message sits at the *end*, leaving the whole transcript as common prefix.

**Bundle finding 21 into the same commit.** `createToolset` (`default-set.ts:74-79`) registers all 21 tools with no capability check, so `database` (1,095 chars), `sql_deploy` (870) and `use_skill` (610) ride every prefix in a workspace where they can only answer "No database is configured for this workspace" (`database.ts:87-93`) / "This session has no skills loaded" (`use-skill.ts:58-62`) — a documented source of confident false statements the diff reviewer is hand-narrowed against (`session.ts:1078-1084`) while the main agent is not. `csharp_nav` (1,182) is dead in a repo with no `.cs`. That is ~1.3k tokens ≈ 2.4 s per main-agent cold prefill, plus an unquantified grammar-narrowing benefit DESIGN §4 endorses. *(`browser` is not in the "cannot succeed" class — BrowserManager is lazy and it works whenever an executable exists. Registration order for the survivors must not change: it is the prefix.)*

**Conflict note.** B1 and finding 21 both mutate the constant prefix and each independently invalidates every warm prefix on the server. Land them in **one** commit, not two.

### B2. Any 220-character paste silently replaces the running task's contract
`core/src/session/contract.ts:92` (finding 3)

`looksLikeTask` returns true on `trimmed.length >= 220` with no other test, and the second branch (≥ 80 chars, 3 sentences split on `/[.!?]\s|\n/`) fires on essentially any 3-line paste. Pasting a 300-char compiler failure mid-task — the single most common message in a coding session — makes `host.ts:1130-1131` pass `distill: true`, and `session.ts:1981` is a bare `this.meta.contract = contract` with no test for an existing unsatisfied contract. The task's goal, criteria and constraints stop being operative (they survive in the transcript, folded into that turn's user message at `session.ts:1988`, until compaction — but message-0 promotion, `meta.contract` and the gate flags are gone). The rest of the session is then audited against criteria distilled from a stack trace. `seedTodos` *is* guarded against clobbering an open plan (`session.ts:2356`); the contract has no equivalent.

**Fix.** When `this.meta.contract` exists and is not `satisfied`, either treat the message as a follow-up or carry `understood`/`premisesChecked` forward so the gates do not re-fire. Separately tighten the length-only branch of `looksLikeTask` to require prose structure — a long paste is not a task.

### B3. Attachments and slash-command expansions replay as the person's own message
`core/src/host/attachments.ts:109` (finding 24)

Record the typed `/name args` alongside a command expansion.

### B4. The diff reviewer is blind to the fixer's edits on exactly the largest turns
`core/src/session/contract.ts:1112` (finding 6)

`buildReviewBrief` keeps the **head**: `diffText.slice(0, DIFF_REVIEW_MAX_CHARS)`. `turnDiffText` appends in transcript order at up to 24,000 chars per `write_file` (`session.ts:1135`), and `freshReview` runs at `session.ts:975` — after the fixer loop and the post-fixer verify — so the acceptance fixer's edits, the freshest and least-checked code in the turn, are what falls off a 160k clip. The reviewer's tools are the read-only five and it cannot recover the dropped hunks. Mitigation the finding under-credits: `read_file` sees current *disk* state, so an edit to a file still named in the surviving head is recoverable; the unrecoverable case is a file whose entire `+++ path (created this turn)` block was clipped, and the clip note carries no inventory of what was dropped. `review-brief.test.ts:43-46` asserts only that the clip is announced.

**Fix.** Budget `DIFF_REVIEW_MAX_CHARS` across `turnDiffText`'s parts newest-first so every touched file is represented, or clip from the middle and list the dropped paths in the notice.

### B5. `write_file` never runs the formatter, so the first later `edit_file` returns a whole-file diff
`core/src/tools/write-file.ts:200` (finding 34)

`grep 'ctx.format' core/src` hits only `edit-file.ts:313-314`; `writeFileTool.execute` goes mkdir → `writeFileAtomic` → return, with no `ctx.format` reference at all. DESIGN.md:160-164 says the formatter "lives INSIDE the write tools" (plural) and that the placement is "the whole reason it exists separately". A created file therefore sits unformatted until the first edit, whose formatter pass rewrites the *entire* file — `renderDiff` strips only a common prefix and suffix (`edit-file.ts:90-131`), so every line lands in removed+added, gets clipped at MAX_DIFF_CHARS = 4000, and the model draws its next SEARCH anchor from the first ~4 KB of a whole-file rewrite. That is precisely the anchoring failure `runner.ts:8-16` says the in-tool placement exists to prevent. The elision notice ("the edit itself was applied in full") is true about the edit and misleading about the file.

**Ordering conflict.** Do **not** land B5 before A1 — adding a formatter call to `write_file` widens the injection surface of `runner.ts:59` from `edit_file` to file creation.

**Fix.** After `writeFileAtomic`, call `ctx.format?.run(args.path, ctx.signal)` and report the post-format byte count plus the "the project formatter reformatted this file" note.

### B6. Unattended runs never close a writing tool card, and the next same-name call takes it over
`app/src/lib/state.ts:1163` (finding 23)

`closeWritingCalls` has four call sites — `turn-started` (712), `step.continuation` (769), `turn.done` (1069), `send-failed` (1089) — and **none** is on a run's path. `startRun` (`composer.tsx:320-390`) dispatches only `user-message` + `run-started` ("turnRunning stays false for a run's whole duration", "a run's turns emit no turn.done"); host-side `runStart` emits only `run.turn` / `run.ended`, and both reducer cases touch neither `items` nor `currentStep`. When a transport error kills a turn mid-argument-stream (`unattended.ts:147-160` counts it and continues), the card stays `writing: true`; `tool.call` matches oldest-first (`state.ts:960-971`) and `pendingTool` skips still-writing cards (`:645-650`), so the *next* turn's arguments and result land on the dead card. Every later same-name call is offset by one, the Changes tab and diff tabs inherit the wrong ordering, and by morning the last card is still animating. The hazard is named verbatim in `turn-started`'s own comment (`state.ts:706-711`) — the guard was added to the one action a run never dispatches.

**Fix.** Call `closeWritingCalls` in `run.turn` and in `run.ended` (with ABANDONED text), clear `currentStep` in `run.ended`. Cheap belt: also on `step.done`, since a step ending proves no `tool.call` for it is coming.

### B7. "None of these" is unanswerable, and the branch written for it is dead code
`app/src/panels/approvals.tsx:217` (finding 9)

### B8. File-ref chips link directories, dates, and two-slash English
`app/src/lib/file-refs.tsx:108` (finding 26)

Executed against the real parser: `core/src/`, `12/31/2026`, `read/write/execute` and `config/.env` all produce refs. ### B9. Two adjacent user messages, and a timeout note naming the wrong limit
`core/src/agent/loop.ts:660` and `:645` (finding 16)

`runStep` appends `{role:'user', content: CONTINUE_NUDGE}` at `:865` and, when the continuation also truncates, returns without appending anything else — so `runTurn`'s `TRUNCATED_TWICE` append lands directly after it. Same for the timeout arm. `session.ts:1987-1988` states the rule this breaks ("two adjacent user messages deviate from the chat template") and folds the contract *into* the user message for exactly that reason; in an append-only transcript the pair is permanent. Separately, `runStep`'s real budget is `coldTimeoutMs ?? **Fix.** Return the budget actually in force with the outcome (`{kind:'timeout'; budgetMs}`) and format from it. For the message pair, fold the follow-up onto the existing nudge's message, or have `runTurn` append to a trailing `role:'user'` rather than after it.

### B10. `git_status` is unusable against any attached folder
`core/src/tools/git-tool.ts:108` (finding 32)

`relative(ctx.workspace.root, abs)` against the **primary** root, with `cwd: ctx.workspace.root` unconditionally. Cross-drive on Windows, `relative()` returns the absolute path, which goes to git after `--` as a pathspec → `fatal: D:/engine/src/a.ts is outside repository`; same-drive gives `../lib/a.ts` and the same fatal. `validate` requires `path` for `blame` (`:70-72`), so blame against an attached folder is unconditionally broken, as is any path-scoped `diff`/`log`. The model gets a raw clipped git message (`:145-152`) — the `not a git repository` special case does not match "outside repository" — so it retries spellings and burns steps. Same `relative()`-returns-absolute family the 2026-08-19 audit fixed in `checkpoints/set.ts:206`; this call site was not covered.

**Fix.** `const mount = ctx.workspace.mountFor(abs)`; refuse plainly if undefined; use `relative(mount.root, abs)` as the pathspec and `cwd: mount.root`. For `status` with no path in a multi-folder workspace, either run per mount and label the sections or say plainly it covers one folder.

### B11. After-tool hooks ignore Esc
`core/src/agent/loop.ts:1269` (finding 14 — one-liner, listed here only because hooks are opt-in)

`return hooks.afterTool(key, result, this.opts.context.signal)` uses the **raw** option; `Session.buildAgent` never assigns `signal` to the ToolContext (`session.ts:3275-3296`), so it is `undefined` and `runPowershell` is bounded only by `TIMEOUT_MS = 60_000` per hook (`hooks.ts:127-129`). `toolContext()` (`loop.ts:1325-1339`) exists precisely to fold the turn signal in, and its own comment records an earlier instance of this same bug.

## Addendum: B1 is only half the prefix, measured against the model's own template

B1 says the divergent `tools` array is what voids the cache. That is true and it is not the
whole cost. The chat template was extracted from `Qwen3.6-35B-A3B-UD-Q4_K_XL.gguf` and both
prompts were rendered with jinja2 and diffed, so these are byte positions, not estimates.

**Two independent divergences, not one.**

1. `tools` renders BEFORE the system prompt — it is the first thing in the prompt:

   ```jinja
   {%- if tools and tools is iterable and tools is not mapping %}
       {{- '<|im_start|>system\n' }}
       {{- "# Tools\n\nYou have access to the following functions:\n\n<tools>" }}
       {%- for tool in tools %}{{- "\n" }}{{- tool | tojson }}{%- endfor %}
       ...
       {%- if merged_system %}{{- '\n\n' + merged_system }}{%- endif %}
   ```

   So a swapped array diverges the prompt at roughly token 10. This is B1.

2. Every gate appends a message with role `user`. That moves `ns.last_query_index`, and

   ```jinja
   {%- if (preserve_thinking is defined and preserve_thinking is true) or (loop.index0 > ns.last_query_index) %}
   ```

   then renders **every assistant message of the current turn without its `<think>` block**.
   The divergence therefore also sits at the current turn's FIRST assistant message —
   which on a long turn is most of what the turn cost to build.

`role: 'tool'` messages are not counted by the `last_query_index` scan (it tests
`message.role == "user"`), so ordinary tool round-trips inside a turn are safe. It is the
gates' appended user message that trips it.

**Measured**, session of 2 tasks / 14 steps, main prompt ~29.5k tokens, at the measured
545 tok/s. One acceptance gate:

| variant | shared prefix | re-prefill |
|---|---|---|
| today (swap tools + append user message) | 113 chars | 29,517 tok ≈ **54.0 s** |
| B1 alone (same `tools` array) | 41,614 chars | 17,989 tok ≈ 32.9 s |
| `preserve_thinking` on the gate only | 7,922 chars | 27,348 tok ≈ 50.0 s |
| **same `tools` + `preserve_thinking` on BOTH sides** | 121,801 chars | 5 tok ≈ **0.0 s** |

Returning to the conversation afterwards: **41.6 s → 0.1 s**.

So B1 shipped alone recovers everything *before* the current turn and none of the turn
itself. On the long turns the gates exist for, that is the majority of the cost, and the
win would look like a third of what B1 predicts — which reads as "the analysis was wrong"
rather than "half the fix landed".

**The full fix, and it costs nothing:** pin `preserve_thinking: true` on *every* request,
and have the harness drop `reasoning_content` from assistant messages of turns that are
over — doing explicitly what the template does implicitly today.

```
prompt size        29,548 -> 29,585 tokens   (+0.1%)
a gate             95.6 s -> 0.1 s
a turn boundary    32.9 s -> 32.9 s          (unchanged, no regression)
per task, 4 gates   6.4 min -> 0.4 s
```

Pinning `preserve_thinking` WITHOUT dropping finished turns' reasoning also works and
additionally makes turn boundaries free, but carries every past turn's thinking in context
(+15% on this session) — which buys prefill time with window, and the window is what
compaction costs minutes over. The drop-and-pin variant above is strictly better.

Two caveats before this is believed:

- This is a static render. The real instrument is `prompt_progress.cache`, which the client
  already parses (`llama/client.ts:323`) — one probe against a live server settles it.
  `client.ts:107-111` records the user already watching one divergent request evict a
  179k prefix, which is the same mechanism.
- `enable_thinking: false` (what `disableThinking` sends today) only affects the generation
  prompt at the TAIL, so it is cache-safe and can stay exactly as it is.

Also worth folding into the same commit: `improveDraft` / `expandDraft` (Ctrl+E) are two
more divergent-`tools` calls that fire while the user is still typing, so improving a
draft silently makes the next send pay a full cold prefill.
