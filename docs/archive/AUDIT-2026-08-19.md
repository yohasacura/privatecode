## HIGH

### 1. restoreFile assigns a file to the wrong snapshot unit when mounts sit on different drives, then reports a delete that never happened

`core/src/checkpoints/set.ts:206`

**Scenario.** Windows multi-drive workspace: primary C:\Users\me\dev\myproject ("app"), attached D:\lib ("engine"). User clicks "Put back" on engine/a.ts. Session.restoreFile (session.ts:1252) passes the absolute path to CheckpointSet.restoreFile, which walks units sorted by root length descending; the guard is `if (rel.startsWith('..') || rel === '') continue`. path.win32.relative('C:\\Users\\me\\dev\\myproject','D:\\lib\\a.ts') returns the absolute 'D:\lib\a.ts' — it neither starts with '..' nor is '' — so the longer-rooted C: unit claims the D: file (Workspace.mountFor at workspace.ts:180 and mounts.ts:186 both add the missing `!isAbsolute(rel)` test; this call site does not). CheckpointStore.restoreFile then runs `cat-file -e <sha>:D:/lib/a.ts` in the C: shadow repo, which fails, takes the "file is new since the checkpoint" branch, `git rm --ignore-unmatch` no-ops, and `rmSync(join('C:\\...\\myproject','D:/lib/a.ts'), {force:true})` silently does nothing. The call returns {removed:true}: the UI reports success, the file is NOT reverted, and session.ts:1256 appends to the transcript "The user reverted engine/a.ts ... (it did not exist then, so it is now deleted)" — a false statement about the disk that the model then acts on. checkpoint-units.test.ts only ever uses two folders under one tmpdir, so the cross-drive case is untested.

**Verified.** The guard is only `rel.startsWith('..') || rel === ''` and omits the `!isAbsolute(rel)` test that workspace.ts:180 and mounts.ts:186 both include, so with units sorted by root length descending (line 203) a longer C: root claims a D: path that path.win32.relative returns absolute, and the C: shadow repo then runs cat-file/rm against 'D:/lib/a.ts'; the reachable call chain is file-view.tsx:95 -> host.ts:464 -> session.ts:1252 (absolute path), and Put back never restores the file (the final rmSync on 'C:\...\D:\lib\a.ts' most likely throws EINVAL rather than returning the claimed silent removed:true, but the misrouting and broken revert are real).

### 2. opensAsWorkspaceRoot only guards the PRIMARY folder, so an attached folder's root can be deleted/moved as if it were a file

`core/src/workspace.ts:75`

**Scenario.** Multi-folder workspace: primary C:\proj (mount "app"), attached D:\engine (mount "engine", access write). ### 5. assistant.text duplicates prose that streamed before a tool call in the same step

`app/src/lib/state.ts:756`

**Scenario.** The model writes prose alongside a tool call in one step (loop.ts explicitly supports this: "Prose that rides along with a tool call is still the model talking to the user"). ### 7. Diff face of an unchanged tracked file renders the whole file as newly added

`app/src/panels/file-view.tsx:186`

**Scenario.** Open any file the session did not touch and that has no uncommitted change (e.g. click `src/app.ts` in the tree), then press the diff glyph in the header. `entry` is undefined so `GitDiffFace` runs: `git.diff {untracked:false}` → `git diff HEAD -- path` returns '', so the code falls through to `git.diff {untracked:true}` → `git diff --no-index -- /dev/null path` (core/src/host/git.ts:73-74), which emits the entire file as `+` lines. Under a control titled "Show what is uncommitted in this file" the user is told every line of a clean file is uncommitted. The `nothing uncommitted in this file` placeholder at line 197 is unreachable for any non-empty file, because the empty-HEAD-diff case is precisely the case that gets replaced by the full-file `--no-index` output. **Verified.** GitDiffFace retries with untracked:true whenever the HEAD diff is empty, and gitDiff's untracked branch is `git diff --no-index -- /dev/null <path>` (core/src/host/git.ts:74), which ignores the index and emits every line of a tracked, unmodified file as `+`; the diff glyph is rendered for any file with no session entry (file-view.tsx:255-263), so the 'nothing uncommitted' placeholder is unreachable for a non-empty file inside a repo.
