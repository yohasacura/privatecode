# Making a turn fast, 2026-09-02

The complaint: one edit costs ten to twenty reads first, and the whole thing crawls. Everything
below was measured against the live server (KAT-Coder-V2.5-Dev on llama.cpp b10665) or read out
of the recorded sessions; nothing here is reasoning from the model's description of itself.

Probes, all runnable: `spike/speed-baseline-probe.mts` (the before/after harness — a throwaway
copy of a real workspace, every step and gate on the clock), `spike/response-format-check.mts`,
`spike/response-format-cache-check.mts`, `spike/enum-grammar-probe.mts`, `spike/map-preview.mts`.
Raw runs: `spike/speed-results/*.json`.

## 1. What the recorded sessions actually show

53 turns over WindowsOptimizer (a 23-file C# project), 766 tool calls:

| tool | calls |
|---|---|
| `read_file` | 285 |
| `edit_file` | 239 |
| `run_command` | 137 |
| `list_dir` | 24 |
| `search_code` | 11 |
| `csharp_nav` | 4 |
| `symbol_outline` | 0 |

Three habits, each a structural gap rather than a model fault:

- **Orientation by crawling.** Before the map existed a turn opened with six `list_dir` calls,
  one directory per step, then read every file whole, one per step: 31 steps before a word was
  said. With the map, the crawl is gone but files are still read WHOLE — a 19k-character
  view-model three times in one turn for edits that touched one method each. The map named
  files and members but never a line, so a ranged read had nothing to aim at.
- **Self-checking after every edit.** Most of the 137 `run_command` calls are `dotnet build` or
  `dotnet test` on the model's own work, the step after each edit — while the harness's own
  check waited for "the run of writes to end" and therefore arrived one step too late, every
  time. A quarter of those commands failed on shape alone (`&&`, `cd <absolute path>`).
- **Nothing to tell it where things are on a big workspace.** The 10k-character map of a
  600-file two-folder workspace named one file in fifteen; the rest was `list_dir`.

## 2. Two findings that changed the plan

### The gates had been off for a week

On llama.cpp b10665, `response_format: json_schema` sent together with the session's `tools`
array is refused — HTTP 400, *"Failed to initialize samplers: failed to parse grammar"* — in
every schema shape. The b10202 build the gates were designed on accepted the pair.
`forcedJson` turns a refusal into `null` by design, so from the server update on 2026-08-28
until this fix every gate — contract, plan, the three lenses, premises, the acceptance audit,
the reviewer's verdict — asked its question, was refused in 0.2 s, and reported "could not
run". The doctor's "contracts 0 of 5 sessions" was this. The fake server in the unit tests
accepts anything, so nothing noticed.

The fix is one field: `tool_choice: 'none'` alongside the array. The template still renders the
tool block, so the prompt is byte-identical and the request stays a pure append — measured
`prompt_n=4`, `prompt_ms≈130` on a warm prefix, constrained 10/10.
`core/test/forced-json.test.ts` pins the request shape; `spike/response-format-check.mts` takes
ten seconds and should run after every server update.

### An enum of workspace paths is dead

The idea from the 2026-08-29 discussion: a forced orientation step whose `open[].path` is an
enum of every file in the workspace, so a path cannot be hallucinated. Measured with the
black-port file list:

| alternatives | wall | decode | what came out |
|---|---|---|---|
| 100 | 6.0 s | 29 tok/s | the same path eight times |
| 500–962 | 0.6 s | — | an empty list |
| 2000 | 22 s | 8.5 tok/s | one plausible file, then `manifest.ts` six times |
| 4000 | 51 s | 4.9 tok/s | eight paths, mostly one file repeated |

Normal decode is ~42 tok/s. The sampler cost grows with the alternatives, and the model does not
choose among paths it cannot see — it emits whatever the grammar admits and repeats it. Small
enums (a few roles, a few actions) stay fine. Orientation on a big workspace has to come from
the prefix, not from constrained choice.

## 3. What was built

1. **The map carries line numbers and a layout.** Every name in the project map has its line
   (`class LeadsController :22: List :53, Get :128`), so `read_file(path, start_line,
   end_line)` for one method is writable from the map alone. A `Folders` block under the
   header lists every folder with its file count and extension mix — twenty-odd lines for
   two thousand files — which is what the model spent its first steps asking one `list_dir`
   at a time. C# files fold their namespace away (they used to render as `namespace App :1:
   Controller :4` with every method invisible). The budget is 20k characters (was 10k);
   `"prefix": { "mapChars": N }` in settings.json overrides.
2. **The prefix is prewarmed at workspace open.** `Session.warmPrefix` asks for one token over
   message 0 plus the tool block the moment a session exists, while the person is still
   typing. The first step then pays for its own message only: 2.3 s instead of 6.7–20 s.
   Cancelled on session switch; a server that is not there leaves things as they were.
3. **The project's check runs right after the step that wrote,** not after the run of writes
   ends, and the prompt says so in one paragraph. The result line lands with the edit's own,
   so the model reads a verdict before deciding what to do next instead of spending a step
   running the build by hand. A failure unchanged since the last check is still one line, and
   the note still says to carry on when the red is unfinished work.
4. **`a && b` in one command entry is split into entries** instead of refused. The refusal
   cost a whole step for a rewrite the harness can do exactly: the entries already run in
   order, in one shell, stopping at the first failure. `||` stays refused.
5. **`tool_choice: 'none'` with every forced-JSON request** (§2).

Not built, and why: a source-prefix (whole files in message 0) only fits small projects and
the owner's workspaces are hundreds to thousands of files; the enum orientation step (§2).

## 4. Before and after

Same probe, same throwaway copy of the real project, same task, gates as they were on each
tree. "Before" is the committed tree (`git worktree` of HEAD), which also means gates off — that
is what the owner's sessions have been running since 2026-08-28.

### WindowsOptimizer, one folder, short task (no contract)

*Add a `SavedAt` property to the Snapshot record and set it in SnapshotStore.Save.*

| | before | after |
|---|---|---|
| whole turn | 51.7 s, 6 steps | **35.0 s, 5 steps** |
| first step (prefix) | 6.7 s | **2.3 s** (prewarmed in 5.7 s while typing) |
| first write at | 17.0 s after 2 read steps | 20.4 s after 3 read steps |
| model running the build itself | 4 commands | **0** |
| harness checks | after the model's own | right after each edit: FAIL → fix → ok |

The reads are the same either way on a project this small; what went was the self-checking
and the cold start.

### black-port, two folders, 335 source files, short task (no contract)

*Add GET api/crm/leads/count-by-status to LeadsController … put LeadStatusCountDto in LeadDtos.cs.*

| | before | after |
|---|---|---|
| whole turn | 73.7 s, 7 steps | **52.8 s, 5 steps** |
| first step | 11.8 s | **4.1 s** (prewarmed in 15.1 s: a 20k map and the tool block) |
| first write at | 46.5 s after 4 read steps, 8 calls | 39.6 s after 4 read steps, 8 calls |
| how it read | whole controller (came back as its shape), then ranged reads, `search_code` | `csharp_nav members`, `find_files`, the shape, three RANGED reads by line, `search_code` |
| model running the build itself | 1, then two re-reads after it | **0** |

On a workspace this size the model already read by range once `read_file` had answered a
whole-file request with the file's SHAPE — that mechanism predates this work. What the map's
line numbers and layout bought is the first two steps: `csharp_nav` and a direct `find_files`
instead of a whole-file read and a guess, and no `list_dir` at all. The rest of the gain is the
cold start and the self-check.

### Long tasks, with every gate firing

The same two tasks, written as a task-shaped request (contract, plan, premises, lenses,
audit). "Before" is what the owner's sessions have been doing all week: the contract call was
refused in 0.3 s and every gate stayed silent.

| WindowsOptimizer, long | before (gates silently off) | after (gates working) |
|---|---|---|
| whole turn | 72.0 s, 7 steps | **136.2 s**, 6 steps |
| contract | 0.3 s (refused) | 14.0 s → 8 criteria |
| premises | — | 11.6 s → 3 assumptions hold |
| lenses | — | 16.9 s → nothing worth asking |
| acceptance | — | 23.7 s → 8 of 8 met |
| plan bookkeeping (`todo_write` steps) | 0 | 2 |
| model running the build itself | 3 | 1 (`dotnet test` for the test it wrote) |

| black-port, long | after (gates working) |
|---|---|
| whole turn | 206.2 s, 11 steps |
| contract / premises / lenses / build / acceptance | 10.1 / 13.2 / 15.4 / 2.0 / 24.9 s |
| the lenses asked a question | yes — and the write it landed on was refused and re-issued: one 755-token generation spent twice |
| plan bookkeeping | 3 `todo_write` steps |

So the gates, working, cost about a minute on a task whose own work takes fifty seconds, and
on both measured turns they found nothing: every premise held, the audit affirmed every
criterion. That is the design doing its job, and it is also the minute the owner will feel
first, because the week's sessions ran without it.

Two things done about that, both structural:

- **Bounds in the grammar.** The contract's `criteria` is capped at six by `maxItems` (the
  prose already said "two to six in total"; the model wrote eight and nine), and the audit's
  `evidence` at 240 characters by `maxLength` (it was writing ~120 tokens per criterion to say
  "the test ran"). Both are honoured by this server's schema-to-grammar
  (`spike/grammar-bounds-probe.mts`); the model's answer to a bound is a longer item, which
  the audit copes with better than three more rows.
- **A profile in settings.json.** `"gates": "thorough" | "fast" | "off"`. `fast` keeps the
  contract and the audit — what holds a task to its goal and catches "done" said early — and
  drops the premise check, the lenses, the fresh reviewer and the plan nudges; the audit then
  runs on every turn that wrote. `off` is the week the owner just had.

| WindowsOptimizer, long | thorough | thorough, bounded | fast | off |
|---|---|---|---|---|
| whole turn | 136.2 s, 6 steps | 167.8 s, 8 steps | **85.9 s, 5 steps** | 72.0 s (the "before" row above) |
| contract | 14.0 s → 8 criteria | 15.4 s → 8 criteria | 12.2 s → 8 criteria | refused |
| premises + lenses | 11.6 + 16.9 s | 12.0 + 13.2 s | — | — |
| acceptance | 23.7 s, 8/8 met | 16.2 s round 1 (6 met, 2 unmet) → 46 s fixer + round 2 → 8/8 | 15.0 s, 8/8 met | — |
| `todo_write` steps | 2 | 2 | 0 | 0 |

| black-port, long | thorough | fast |
|---|---|---|
| whole turn | 206.2 s, 11 steps | **109.9 s, 7 steps** |
| contract + acceptance | 10.1 + 24.9 s | 14.2 + 17.1 s |
| premises + lenses (+ the refused write) | 13.2 + 15.4 s (+ ~20 s) | — |
| `todo_write` steps | 3 | 0 |
| model running the build itself | 2 | 0 |

**Then `fast` got its own contract.** A goal, at most four criteria and the two flags the
gates key on — no rules, constraints or interfaces, because the audit is the only consumer left
in that profile and it audits criteria. The distillation fell from 12–14 s to 5–6 s and the
audit from 15–17 s to 9–10 s, so the whole of `fast` is now about fifteen seconds on top of a
turn with no gates at all:

| long task, `fast` with the lean contract | whole turn | contract + audit |
|---|---|---|
| WindowsOptimizer | **71.2 s** (off: 72.0, thorough: 136.2) | 4.9 + 10.0 s → 4 of 4 met |
| black-port | **93.5 s** (thorough: 206.2) | 5.8 + 9.1 s → 4 of 4 met |

Two honest notes on the bounds. The model fills whatever the grammar allows: with rules
capped at three and criteria at five it produced exactly eight rows again, so the cap on
COUNT bought nothing on this request, while the cap on evidence LENGTH cut an audit round
from ~24 s to ~16 s. And the bounded thorough run is the slowest row not because of the
bounds but because its first audit judged two criteria unmet (the test the model had written
had not been shown to run) and the fixer round did what it is for: 46 s, then 8 of 8. That is
sampling variance on top of the gate's design, and it will happen on any profile that audits.

## 4a. Server-side: two flags tried

**Slot save/restore makes resume instant, and is built in.** With the server started under
`--slot-save-path`, `/slots/0?action=save` wrote a 20k-token state (453 MiB) in 0.4 s and
`restore` read it back in 0.5 s — across a server restart — and the resumed conversation then
prefilled 22 tokens instead of 19,900 (`spike/slot-save-probe.mts`). One thing decides
whether it works: this model's recurrent state cannot be rewound, so the saved sequence must
be a PREFIX of the next prompt. That is true right after a turn's final message (the reply is
rendered back verbatim) and false after any gate has asked its forced question — so the
session saves at exactly that moment, at most every three minutes or 20k tokens
(`Session.saveSlotIfDue`), one file per workspace labelled by `state/slot.json`, and the host
restores it on resume before the ordinary warm-up (`Session.restoreSlot`). A server without
the flag answers 501 once and is not asked again. The launcher's `config.json` now carries
the flag in `ExtraArgs`.

**N-gram speculative decoding is a loss here.** The MTP head drafts at ~65% acceptance on a
verbatim copy (45 tok/s against ~42 plain). Adding `ngram-map-k4v` beside it
(`--spec-type draft-mtp,ngram-map-k4v`, server restarted by hand — `spike/server-restart.ps1`)
drafted twice as many tokens and accepted the same number, so the verification cost is paid
for nothing: 26–39 tok/s on the same task (`spike/spec-types-probe.mts`). The reason is the
shape of what the agent copies: `read_file` hands the model NUMBERED lines and `edit_file`
takes them back without the numbers, so the n-grams the lookup needs are never in the
context verbatim. Per-request `speculative.types` is accepted and ignored by this build.
Reverted to MTP alone.

## 4b. Two axes, and what "Checks off" now holds

The composer's **Checks on / off** chip (`gateMode`, per session) and the settings profile
(`gates`) are different questions: the chip is WHEN — by itself, or when asked with
`/check` and `/review` — and the profile is WHAT exists at all. Every recorded session of the
owner's ran with the chip on; the chip was never the reason a gate did or did not run.

Until this pass the chip kept only its second half. Off, the post-turn chain waited as
promised, but the pair at the first write (premises, lenses) and the build after every edit
ran anyway — forty seconds of gates on a turn the person had told to stop checking. Now
"off" holds all of it, the contract still distils (so `/review` has something to review
against), and the prompt's "the check runs by itself" paragraph is left out of a session
that starts with the checks off. And an explicit `/review` runs the reviewer whatever the
profile says: `fast` decides what runs by itself, never what a person may ask for by name.
`core/test/checks-off.test.ts` pins both.

## 5. What is next, in order

1. Decide the default profile. The numbers above are the argument either way; `thorough`
   is what ships until the owner says otherwise, because turning a safety gate off by default
   is not a speed fix.
2. The lenses' question lands on a write and refuses it, so the generation that produced the
   write is paid twice. Asking right after the first READ step instead — the model has opened
   what it opened, and nothing has been generated that a refusal would waste — is the next
   thing to measure.
3. A deterministic harness-side pack for task-shaped requests on big workspaces: ripgrep the
   identifiers the request names, hand over the OUTLINES of the files that hit in one appended
   block before the first step. Code decides, no generation spent. The black-port runs read
   well enough without it that this is a measurement to take, not a certainty.
